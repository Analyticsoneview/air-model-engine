# AIR Telegram notifications

Telegram notifications are sent to configured private and group destinations. The bot token is never stored in source control.

## Backend configuration

For Docker Swarm, create a secret from the **replacement token** generated by BotFather:

```sh
printf '%s' 'YOUR_REPLACEMENT_BOT_TOKEN' | docker secret create air_telegram_bot_token -
```

Attach `air_telegram_bot_token` to the backend service and set:

```text
AIR_TELEGRAM_BOT_TOKEN_FILE=/run/secrets/air_telegram_bot_token
AIR_TELEGRAM_CHAT_IDS=PRIVATE_CHAT_ID,GROUP_CHAT_ID
AIR_TELEGRAM_DEDUPE_DB_PATH=data/air_telegram_notifications.sqlite3
```

Use the configured private and group chat IDs supplied by the AIR operator. Persist the deduplication SQLite file on durable backend storage so restarts do not resend the same candidate/status alert.

## Test

After deploying the backend with the secret and chat IDs configured, call the authenticated endpoint:

```http
POST /api/v1/model-engine/telegram/test
```

A successful response reports the number of destinations reached. Never send the bot token to the mobile app, Telegram group, GitHub issues, or source control.

## Alert semantics

- RECOVERED: active recovery watch candidates are labelled as watch/backtest only, not live positions.
- EXPIRY78: replay candidates and lifecycle changes are sent as research alerts; no broker orders are placed.
- EXPIRYSCAN: only `LIQUIDITY_SCREEN_PASSED` rows are sent, explicitly labelled as a liquidity-screen pass, not a full AIR QOC trade qualification. The current EXPIRYSCAN engine reports zero qualified trade signals.
- Delivery is idempotent per candidate, status, and destination. Failed deliveries are eligible for retry on the next API scan.
- Notifications are triggered when the corresponding authenticated strategy endpoint is requested. A separate always-on scheduled worker is required for alerts when no client is polling those endpoints.
